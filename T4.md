# T4 Formats and Operations

T4 uses the existing FastAPI, SQLAlchemy, and SQLite stack. The additive tables are `issued_records`, `webhook_subscriptions`, and `webhook_deliveries`; startup `Base.metadata.create_all()` creates them for existing installations. No existing event or project rows are rewritten.

## Signed Records

The record envelope is JSON with `id`, `payload`, `signature`, `key_id`, and `public_key`. The payload contains schema `version`, deterministic `record_id`, `record_type`, `event_id`, public `event_name`, stable `subject_id`, UTC `issued_at`, and a record-specific `data` object. It does not include email addresses, tokens, score comments, or raw score values.

Record types are `participant_certificate` and `judge_participation`. Certificates are issued for registered participants and include their submitted project count. Judge participation records are issued for judges with submitted-project scores and include the count of scored projects.

Signatures use Ed25519 over canonical JSON encoded as UTF-8 with sorted keys, compact separators, Unicode preserved, and non-finite numbers rejected. `signature` and raw 32-byte `public_key` are standard Base64. `key_id` is the first 24 lowercase hex characters of SHA-256 over the raw public key. A verifier can reproduce the canonical bytes and verify the signature with any Ed25519 implementation.

The private key is an unencrypted PKCS#8 PEM file at `data/t4_ed25519_private.pem` by default. `DOGFOOD_SIGNING_KEY_PATH` can override this path. The file is created once with restrictive mode where supported. Missing keys are generated; invalid or non-Ed25519 key material is not overwritten, and signing APIs return 503. The private key is never returned by an API. Public verification accepts only the active public key, so replacing the signing key requires re-issuing records if old records must remain verifiable by this service.

`POST /api/events/{event_id}/records/generate` is organizer-only and idempotent by event, record type, and subject. Public retrieval is `GET /api/t4/records/{record_id}`. Stored and detached verification are available at `GET /api/t4/records/{record_id}/verify` and `POST /api/t4/records/verify`. The active public key is available at `GET /api/t4/signing/public-key`.

## Webhooks

Subscriptions are organizer-only. `POST /api/webhooks` creates a global subscription; `POST /api/events/{event_id}/webhooks` creates an event-scoped subscription. Use the matching `GET` routes to list and `DELETE` routes to disable. Delivery status is listed at `GET /api/events/{event_id}/webhooks/deliveries`.

Supported event types:

- `event.created`, `event.updated`
- `participant.registered`, `track.created`
- `team.changed` for create, rename, and membership changes
- `project.changed` for create, update, and submission
- `judge.score_submitted`
- `community.changed` for voting settings, votes, and comments
- `record.issued`
- `webhook.subscription_changed` for event-scoped subscription changes
- `data.imported`

Each callback is an HTTP POST JSON envelope with `delivery_id`, `event_type`, `event_id`, UTC `timestamp`, and event-scoped `payload`. Payloads omit emails, score values, comment bodies, credentials, and secret material. The delivery ID is a stable SHA-256-derived ID from subscription, event, type, action, source key, and canonical payload. Identical logical deliveries are deduplicated.

The sender allows globally routable and loopback IP destinations, rejects credentials/fragments and private/link-local/reserved addresses, rechecks destinations before delivery, refuses redirects, and uses a 1.5-second timeout. A receiver failure is stored as a failed delivery and does not roll back the primary user action. The deterministic delivery ID hashes the subscription, event, type, action, source key, event timestamp, and canonical payload. Loopback receivers support deterministic offline tests.

## Gallery Embed

`GET /embed/events/{event_id}/gallery` serves a standalone iframe-ready HTML page without authentication. It queries only submitted projects and renders only event name, project title, and project summary. Drafts, participant emails, judge scores, voting totals, tokens, and signing keys are not included.

## Bulk Archive Schema

Export is organizer-only at `GET /api/events/{event_id}/bulk-export`; import is organizer-only at `POST /api/events/bulk-import` with `{"target_event_id":"...","archive":{...}}`.

Schema version 1 contains:

```json
{
  "schema_version": 1,
  "event": {"id": "source-id", "name": "Event", "description": "", "submissions_close": "2027-01-01T00:00:00Z"},
  "tracks": [{"id": "track-id", "name": "Track"}],
  "registrations": [{"user_id": "user-id", "email": "participant@example.org"}],
  "teams": [{"id": "team-id", "name": "Team", "members": [{"user_id": "user-id", "email": "participant@example.org"}]}],
  "projects": [{"id": "project-id", "team_id": "team-id", "track_id": "track-id", "owner_id": null, "title": "Project", "summary": "", "repo_url": "", "status": "submitted", "submitted_at": "2026-09-01T00:00:00Z"}],
  "judge_assignments": [{"judge_id": "judge-id", "track_id": "track-id", "user_id": "judge-user-id"}],
  "scores": [{"id": "score-id", "judge_fixture_id": "judge-id", "judge_user_id": "judge-user-id", "project_id": "project-id", "criteria": {}, "comment": "", "scored_at": "2026-09-01T00:00:00Z"}],
  "voting_config": null
}
```

Registrations and team members resolve to existing accounts by ID, then email; an unknown registration account is rejected. Webhook destinations, deliveries, votes, comments, issued records, auth tokens, and password hashes are intentionally excluded. Import targets must be fresh IDs and cannot be `evt_01` or `evt_t3`; colliding track, team, project, and score IDs are deterministically remapped. Malformed or unsupported archives return 4xx errors and do not overwrite existing event data.
